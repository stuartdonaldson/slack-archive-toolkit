# Review — LLM context pack migration plan

_Reviewed 2026-08-06 against `docs/llm-context/MIGRATION-PLAN.md`, `docs/llm-context/README.md`, and the current `docs/` tree, `README.md`, and `scripts/nightly-backup-digest.sh`._

## Verdict

The **structure is sound and worth building**. Splitting schema contract / query policy / domain background / dated augmentation is the right decomposition: it matches how the material actually changes (schema changes with code, policy changes with practice, augmentation changes on a manual refresh cadence), and it fixes the current state where evidence-precedence rules are duplicated in `docs/slack-ingestion.md` and `docs/report-queries.md`.

Three things block it as written:

1. The target layout **does not account for the whole upload set the project already ships** — two prompt docs the nightly script copies are missing from the plan entirely.
2. The plan **silently changes the evidence-precedence ranking** rather than declaring it as a decision.
3. `README.md` is doing three jobs at once (repo guide, project instruction, prompt library) — the same conflation the migration exists to remove — and neither of the two real deployment modes (one-off session vs. ChatGPT Project, the latter capped at 8,000 characters of always-resident instruction) is designed for.

Findings are ordered by what would cause damage if left unaddressed.

## P1 — Must resolve before Phase 2

### P1-1. The pack omits the task-prompt layer, and the nightly copy list will break

`scripts/nightly-backup-digest.sh:33-39` copies **five** docs into `~/slack-exports/` every night:

| Copied doc | In the plan? |
|---|---|
| `docs/slack-ingestion.md` | yes → `ingestion-contract.md` |
| `docs/report-queries.md` | yes → `query-policy.md` |
| `docs/f3-culture.md` | yes → `f3-domain-context.md` |
| `docs/newsletter-prompt.md` | **no** |
| `docs/fng-getting-started-prompt.md` | **no** |

`README.md` §Documentation and workflow steps 7–8 also route users to those two prompt docs. The plan's target layout has no home for them, and Phase 5 does not list them — so after retirement the pack covers three of the five files the workflow actually uses, and the nightly copy list ends up split across two directories with no stated owner.

**Recommendation:** add a `prompts/` subtree to the target layout and bring the task prompts in:

```text
docs/llm-context/
├── README.md                 # repo-facing: what the pack is, how to assemble an upload
├── project-instructions.md   # <=8000 chars, paste-ready ChatGPT Project instruction
├── session-preamble.md       # first-message instruction for a one-off ChatGPT session
├── ingestion-contract.md
├── query-policy.md
├── f3-domain-context.md
├── prompts/
│   ├── initial-intake.md
│   ├── regional-slt.md
│   ├── ao-directory.md
│   ├── authority-routing.md
│   ├── newsletter.md          # from docs/newsletter-prompt.md
│   └── fng-getting-started.md
└── augmentations/
    ├── README.md              # index: which snapshot is current
    ├── f3-nation-operations.md
    └── f3-nation-admins.md
```

Make Phase 4 concrete: the nightly copy list becomes one directory copy (`cp -r docs/llm-context/ ~/slack-exports/context/`), which removes the per-file maintenance that caused the drift in the first place.

### P1-2. The plan changes evidence precedence without declaring it a decision

Three precedence lists now exist and they do not agree:

| Rank | `slack-ingestion.md` / `report-queries.md` (8 items, identical) | MIGRATION-PLAN §Source authority model (7 items) |
|---|---|---|
| 1 | Current extracted canvas/file content | Canvas/file content **and** channel topic/purpose merged into one rank |
| 2 | Current channel topic/purpose | Announcement by role holder |
| 3 | Announcement by role holder | Structured digest fields |
| 4 | Structured digest fields | Message/thread evidence |
| 5 | Message/thread evidence | **Dated manual augmentation** (new rank) |
| 6 | File metadata without extracted content | Profile title/display name |
| 7 | Profile title/display name | Inference |
| 8 | Inference | — (`file metadata without content` dropped) |

Two substantive changes are buried in a migration plan: collapsing ranks 1–2, and dropping "file metadata without extracted content". The one genuinely new element — where a dated augmentation sits — is the whole reason the pack exists and deserves to be explicit.

**Recommendation:** keep the existing 8-rank list verbatim in `query-policy.md` — do not collapse ranks 1–2 (`docs/slack-ingestion.md` §Channel context fields has a worked rationale for topic/purpose being distinct from, and weaker than, maintained canvas content) and do not drop rank 6. Then add dated augmentation as a **conditional rank with a recency tiebreaker**, which is what the plan's own prose already argues in §Source authority model:

> A dated augmentation is the **primary** source for a fact the Slack exports structurally cannot express (e.g. the F3-Nation regional admin list). For a fact the exports *can* express, it ranks immediately below message/thread evidence (rank 5).
>
> **On conflict, compare dates, not just ranks.** Weigh the augmentation's `collected:` date against the competing evidence's own date — the message's post date, the canvas's currency per §Canvas/file currency ranking, or the profile's last-observed date. Take the more recent as the working answer, report the losing source alongside it, and lower the confidence label to reflect the conflict. A dated augmentation that post-dates an inference or a stale profile title is very likely correct; one that pre-dates a direct announcement is very likely superseded.
>
> Never resolve a conflict silently, and never present an augmentation-derived fact without its collection date.

This needs a label for "we picked a side but the sources disagree" — the current vocabulary has no such value. `Unresolved` means *no answer*; this case *has* an answer that is merely weak. Add one:

| New label | Use when |
| --- | --- |
| `Contested` | Sources materially disagree. The stated answer is the more recent/stronger one; the conflicting source and both dates are reported alongside it. |

Confidence should also degrade by **how the augmentation was collected**, which the pack currently does not record. Add a `fidelity:` field to the augmentation header block (P2-3) and map it in `query-policy.md`:

| `fidelity` | Meaning | Best label it can support | On conflict with dated Slack evidence |
| --- | --- | --- | --- |
| `system-extracted` | Transcribed directly off a system screen (e.g. `/f3-nation-settings`) | `High` for its collection date | `Contested`; augmentation stated first if newer |
| `hand-compiled` | Assembled by a person from several sources | `Medium` | `Contested`; both sides stated, neither asserted |
| `recalled` | From memory or informal report | `Working signal` | `Unresolved`; do not assert over dated Slack evidence |

The existing roster is `system-extracted` (manual `/f3-nation-settings` extraction, 2026-06-30), so it earns `High`-for-its-date and its conflicts with rank 7–8 signals should resolve in its favor under a `Contested` label. Record the whole rule as an ADR under `docs/adr/`: it changes how every report resolves a conflict, and it adds a label to a vocabulary three documents currently share.

### P1-3. `ingestion-contract.md` will drift from the emitted schema, with no mechanism to stop it

The pack restates the v4 contract — `slack-llm-digest-v4`, `slack-llm-files-v1`, the `workspace + channel_id + id` join key, `archive_status` values. The authority for all of that is `docs/DESIGN-export.md` §`files_out` sidecar / §schema v4 and `docs/adr/0004-digest-v4-files-sidecar.md`. Nothing in the plan ties them, and this project has already paid for that once — the work-log records a v4 rewrite that shipped two factual errors against the real schema (`archive_status` values, an unneeded `message_ts` normalization).

**Recommendation:**
- State in the plan that **`docs/DESIGN-export.md` is the schema authority**; `ingestion-contract.md` is a derived, consumer-facing restatement and never the place a schema fact is decided.
- Put the covered schema versions in a header line of `ingestion-contract.md` so a mismatch is visible on upload.
- Add a placement rule to `CLAUDE.md` §Placement Rules: _digest/profile/sidecar schema change → `docs/DESIGN-export.md` + `docs/llm-context/ingestion-contract.md`_, so `/doc-trigger-check` catches it.

### P1-4. Factual error to carry forward: the sidecar is not run-matched

`README.md` (llm-context) says _"The digest and sidecar must refer to the same export run"_ and lists **unmatched sidecar records** as a validation concern. Per `docs/DESIGN-export.md:366-384`, `files_out` is **cumulative across runs, not window-relative** — each run merges into whatever already sits at the path, and entries from channels outside the current window are deliberately retained rather than pruned.

So sidecar records with no digest reference are the **expected steady state**, not a gap. As written, the pack will make an LLM report a normal condition as a data problem on every single ingestion.

**Recommendation:** in `ingestion-contract.md`, state the asymmetry directly: a digest file reference with `has_content: true` and no sidecar match **is** a gap; a sidecar record with no digest reference is **normal** and should be reported only as a count, not a warning. Note also the wording gap between `docs/DESIGN-export.md:509` ("no text was ever extractable") and `docs/slack-ingestion.md` ("no extracted text is available in this snapshot") — pick one and make `archive_status` the tiebreaker.

### P1-5. Two deployment modes exist and only one is designed for

The pack is deployed two ways, and the plan treats them as identical:

| | **One-off ChatGPT session** | **ChatGPT Project** |
|---|---|---|
| Rules live in | The first message — fully in context | The Project instruction box — **hard cap 8,000 characters** |
| Context files | Uploaded per chat, fully in context | Project knowledge, **retrieved on demand — not guaranteed in context** |
| Run artifacts | Uploaded with the chat, always current | Stale the moment a newer digest exists |
| Failure mode | Long first message | A rule in a knowledge file silently never gets retrieved |

The second column is the one that bites. In Project mode a knowledge file is *searched*, not *read* — so any rule that must apply to **every** answer cannot live only in `query-policy.md`. If "never merge an `ambiguous` mention entry" or "Slack admin ≠ F3-Nation admin" sits only in a knowledge file, it applies exactly when the retriever happens to surface it. The 8,000-character instruction box is not a summary of the pack; it is the only guaranteed-resident surface, and it has to carry every invariant.

**Recommendation:** make the split explicit, as two maintained files.

- **`project-instructions.md`** — verbatim paste into the Project instruction box. Carries the **invariants**: schema names and the sidecar join key, the sidecar asymmetry (P1-4), workspace-local identity and the ambiguous-merge prohibition, Pacific time, the 8-rank precedence list, the augmentation rule and `Contested` label (P1-2), authority non-equivalence, the canvas-currency asymmetry, link/citation requirements, and the first-message consistency check (P2-6). It **points at** the knowledge files for detail — table layouts, field-by-field schema semantics, validation counts, culture — none of which must be resident to be correct.
- **`session-preamble.md`** — the one-off variant, deliberately thin: everything is already in context, so it needs only "read `ingestion-contract.md` and `query-policy.md` first, run the consistency check, produce no substantive report until asked."

**The 8,000-char budget is comfortable, not tight.** I drafted a complete invariant ruleset covering every item listed above and measured it at **4,410 characters** (619 words) — roughly 3,600 characters of headroom for F3-specific additions. The draft is in this session's scratchpad at `proj-instr-draft.md` and can seed Phase 2. Two rules follow from the cap:

- Add a character-count check to the repo's lint/CI step so an edit that overflows the box fails here rather than in the ChatGPT UI.
- State in `README.md` that **run artifacts — digest, sidecar, profiles — do not belong in Project knowledge.** They are monthly and go stale, and a Project holding a three-month-old digest will answer confidently from it. Project knowledge holds the pack; run artifacts are uploaded per chat. If a Project *is* deliberately loaded with resident data, its instruction must name that data's `as_of` date so the staleness is visible in every answer.

## P2 — Fix during Phase 2

### P2-1. `README.md` conflates three audiences

It is simultaneously the repo-facing explanation, the ChatGPT Project instruction (§Recommended project instruction), and the prompt library (§Reusable prompts) — while not itself being in the "Intended upload set". An operator following it has to hand-extract a blockquote and five prompts out of a file they were told not to upload.

**Recommendation:** split per the P1-1 layout. `README.md` keeps assembly instructions, source roles, and maintenance rules; `project-instructions.md` is paste-ready; each prompt is its own file so it can be uploaded or pasted individually. Relatedly, `README.md`'s §Sources to curate duplicates the plan's target-file table — after Phase 2 the plan's table is history and the README's is live; delete one.

### P2-2. Phase 2's "move content rather than copy" contradicts the plan's own goals

Phase 2 says _"Move content rather than copy it where possible"_, but Goals say _"Preserve the existing documents until their replacements have been reviewed"_, Non-goals say _"Change existing documentation... in this planning increment"_, and Phase 5 is the retirement step gated on Phase 3 validation. Moving content in Phase 2 empties the legacy docs before validation — while `scripts/nightly-backup-digest.sh` is still copying them nightly. The nightly upload set would silently degrade between Phase 2 and Phase 4.

**Recommendation:** Phase 2 **copies**. Add to each legacy doc a one-line header — _"Transitional. Canonical home: `docs/llm-context/<file>`. Do not edit."_ — which delivers single-canonical-home without emptying a file that automation still reads. Deletion happens once, in Phase 5.

### P2-3. Dated filenames make every reference go stale

`augmentations/f3-nation-admins-2026-06-30.md` bakes a date into the path. On the next refresh, `README.md`, the plan, the nightly script, and any project instruction all point at a stale file, and the directory accumulates snapshots with no marker for which is current. The existing `docs/f3-it-infrastructure-augmentation-2026-06-30.md` already demonstrates the failure — it names `f3-digest-2026-06-30.json` and `f3-user-profiles-2026-06-30.json` as its upload companions, filenames that no longer describe any current export.

**Recommendation:** stable filenames, dated **content**: `augmentations/f3-nation-admins.md` with a required header block (`collected:`, `source:`, `collected_by:`, `fidelity:` per P1-2, `coverage:`, `known_gaps:`, `refresh_trigger:`, `refresh_owner:`). Archive superseded snapshots under `augmentations/archive/<name>-<date>.md` if history matters. Add `augmentations/README.md` as the index so "any applicable dated augmentation" in the upload set is a lookup rather than a judgment call.

### P2-4. `f3-culture.md` fails the plan's own validation checklist today

The checklist says _"The culture file contains background and style guidance, not current leadership or authority assignments."_ The current `docs/f3-culture.md` attributes eight substantive claims to a named person (Columbia) with Slack permalinks, including a **Cascades leadership vision** framing (lines 19, 31, 111-114). That is dated message evidence about a specific person's regional leadership posture, sitting in a file the pack declares "background only; not proof of a current role".

**Recommendation:** make this an explicit Phase 2 work item, not an implicit one. When porting to `f3-domain-context.md`, either de-attribute the cultural framing (the ideas are F3-general, not Columbia-specific) or move the sourced quotes into a clearly-labeled §Source notes section that the query policy ranks as message evidence. Don't port as-is.

### P2-5. Phase 3 exit criteria are not testable

_"Answers preserve source links, separate authority types, label uncertainty"_ is a judgment call made once by whoever runs it. The pack's entire value is that an LLM behaves consistently after a schema bump — which is exactly when it gets re-validated by someone with less context.

**Recommendation:** write `docs/llm-context/validation-set.md`: 8–12 golden questions with the **expected evidence type and confidence label** (not expected answers, which change with the data). Draw them from the failure modes the docs already name — F3-Nation admin vs. Slack admin confusion, an `ambiguous` mention entry, a canvas with empty `modification_history`, a channel whose `topic` and `purpose` conflict, a `has_content: false` file. Phase 3's exit criterion becomes "the validation set passes", and it is re-runnable on every schema bump.

### P2-6. Add a consistency and drift analysis to ingestion — and push the deterministic half into the exporter

`docs/slack-ingestion.md` §Initial ingestion validation already counts files, sidecar matches, and unmatched records. That is **coverage** checking, not **consistency** checking, and it stops at the boundary of a single upload. It never looks for internal contradictions, and it cannot notice that a pairing rate is degrading run over run — which is the signal that an *input* needs refinement rather than a one-off gap worth a sentence.

**Recommendation — extend the check to three classes:**

1. **Referential integrity** (within the upload): digest file refs ↔ sidecar records in both directions, with the P1-4 asymmetry applied; each file's `message_ts` ↔ a real digest message `ts` in the same workspace/channel; message `mentions` ↔ `user_index`; `leadership.by_region` names ↔ resolvable profiles; `channel_id` uniqueness per workspace; `in_scope:false` parents actually having an in-scope reply.
2. **Cross-source consistency** (upload ↔ augmentation ↔ profiles): roster names that resolve to no profile in that workspace; regions present in an augmentation but absent from the digest, and the reverse; a role asserted by an augmentation that newer Slack evidence contradicts — this is exactly the P1-2 `Contested` path, and the ingestion pass should surface it **up front** rather than discovering it mid-answer; and the augmentation's `collected:` date versus the digest's `as_of`, so a roster older than the data is flagged before it is used.
3. **Drift** (this upload vs. the last): sidecar match rate, extracted-content coverage, unresolved-mention count, channels with neither `topic` nor `purpose`. A match rate falling run over run means an input needs fixing, not that one answer needs hedging.

**Split it by who can do it reliably.** Classes 1 and 3 are deterministic joins and counts over the emitted documents; an LLM's version is best-effort, non-reproducible, and burns context on arithmetic. Emit them from code instead — a `consistency` block written by `export digest` carrying the counts, the specific unmatched keys, and the prior run's values for comparison. The pack's job then shrinks to *reading and reporting* that block, which is reliable, plus class 2, whose cross-source semantic judgments code has no basis to make.

That is a code change, so it belongs in bd rather than the migration plan: file it against the export pipeline (`src/slackbackup/export_logic.py`, alongside the existing `merge_files_out` bookkeeping), and have `ingestion-contract.md` specify the reporting contract for whatever the block contains. Until it exists the LLM-side check is the interim — write it into `ingestion-contract.md` now, structured so the deterministic half can later be swapped for the emitted block without rewriting the prompt.

## P3 — Worth doing, not blocking

- **`docs/f3-it-infrastructure-augmentation-2026-06-30.json` has no code consumer.** Verified by grep across `src/`, `scripts/`, `tests/`, and `jobs/` — the only reference is the companion `.md`. Record that in the plan's Phase 5 table so the removal condition reads as **already satisfied** rather than an open question.
- **Drop the `.md`'s "How to use this with LLM uploads" section entirely** when splitting. It instructs uploading the JSON alongside two dated filenames that no longer exist. It should not survive into either augmentation file.
- **`files_out` is internal jargon** in an LLM-facing doc (llm-context `README.md` §Upload for each reporting run). It is a job-config field name. Use the schema name `slack-llm-files-v1` in anything an LLM reads.
- **Untracked `docs/sotn-2026-07-30.md`** (62 KB raw State of the Nation transcript) is an undeclared dated external artifact. It is neither in the plan nor in `.gitignore`. Decide: `augmentations/` with proper provenance headers, or out of the repo.
- **`docs/llm-export-suggestion.md`, `docs/llm-digest2-idea.md`, `docs/llm-leadership-improvement.md`** are historical external feedback, cited by `src/slackbackup/handlers/f3.py`, `docs/DESIGN-export.md`, and ADR-0001. They are correctly out of scope — say so explicitly in Non-goals so a later cleanup pass doesn't sweep them up with the other `llm-*` files.
- **State a size budget.** "Concise enough to upload with a digest" is untestable. The current sources total ~42 KB (~11k tokens); a stated ceiling (say 60 KB for the always-upload set) makes the goal checkable.
- **No owner or cadence for augmentation refresh.** The plan requires every augmentation to state a refresh *trigger* but names no owner and no review interval. Add both to the required header block (P2-3).
- **Phases aren't tracked.** Per `CLAUDE.md`, all task tracking is bd. File one issue per phase with Phase _n_ → Phase _n+1_ dependencies; the P1 items above are Phase 1 blockers.
